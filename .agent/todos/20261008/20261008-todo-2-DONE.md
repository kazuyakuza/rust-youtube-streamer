### 2. Establish the Minimal Cargo Project [DONE]

- Add a root `Cargo.toml` for a single Rust executable package named consistently with the existing project, using a valid Rust crate/package name such as `rust-youtube-streamer-service`.
- Use a current stable Rust toolchain in the container and document the chosen edition. Do not add dependencies speculatively.
- Add `src/main.rs` with only the smallest idiomatic entry point needed to prove the package builds.
- Do not create empty module files for all future features merely to match the target architecture. Feature modules will be introduced by their respective phases.
- Generate and commit `Cargo.lock` as appropriate for the executable package.
- Do not implement configuration parsing, logging infrastructure, OAuth, YouTube API calls, rendering, chat handling, or FFmpeg process management in this phase.

### 3. Establish Reproducible Docker-Based Development Checks [DONE]

The implementation environment does not have Rust/Cargo installed. Do not attempt to validate the project by invoking host-installed `cargo` or by installing Rust into the implementation environment.

Use the MCP available in the user's local implementation-agent environment to access the Alpine VM. The project directory is shared with that VM, and Docker commands can be executed there. First inspect the available MCP tools and follow their documented invocation requirements.

- Add the minimal Docker build configuration required to run Rust/Cargo commands reproducibly from the Alpine VM against the shared project directory. Use a maintained official Rust image or another justified, maintained image; pin the image to a deliberate stable version rather than using an unqualified floating tag. The host VM being Alpine does not require the Rust container image itself to be Alpine-based.
- Choose either a `Dockerfile` plus Compose configuration, or an equally clear minimal Docker setup. Prefer a Compose service if it makes the standard commands easy to run consistently. Avoid adding multiple overlapping build mechanisms.
- Ensure the project directory is mounted into the container and Cargo operates on the shared source tree. Ensure generated files such as `Cargo.lock` remain available in the shared directory after commands finish.
- Ensure the container can write generated files without leaving project files owned by an unexpected user where feasible. Document any UID/GID or permission handling required by the chosen setup. Do not use privileged containers or request administrator elevation for the application.
- Document the exact Docker commands used to run each check through the VM's Docker engine. Adapt command syntax to the actual MCP and VM environment rather than assuming an unavailable shell or connector.
- Run the following commands inside the Rust container, against the mounted project:
  - `cargo fmt --check`
  - `cargo check --locked` after `Cargo.lock` has been generated
  - `cargo test --locked`
  - `cargo clippy --locked -- -D warnings`
- If formatting needs to be applied first, run `cargo fmt` in the container and then re-run `cargo fmt --check`.
- Run the checks sequentially where generated lockfile or build output from an earlier command is required.
- Confirm the exact command exit status/results from the MCP/VM execution output. If a command cannot be run, report that fact and its reason. Do not report an unexecuted command as passing.
- Do not claim Windows or Linux runtime validation just because a Linux container was used on the Alpine VM. Report the actual VM/container environment and the scope of validation precisely.
- Do not set up CI or a deployment image in this phase; the Docker setup here is for local development/build checks only.

## Platform and Runtime Constraints

- Windows and Linux are intended development/runtime targets; Ubuntu Server is the production target.
- The application will be launched directly by the user. Do not register it as a Windows service, install it as a system service, create a service wrapper, or introduce an installer.
- FFmpeg is an external prerequisite that the user installs or provides separately. Do not download, install, bundle, or configure system-wide FFmpeg as part of this phase.
- The application and FFmpeg are assumed to run under a normal user account with the required read/write permissions to the chosen files and directories. Do not add administrator-elevation behavior.
- Detailed FFmpeg prerequisite/configuration and Windows execution guidance belongs in the appropriate later documentation task, in a document linked from the README. Do not expand Phase 00 into that full guide.
