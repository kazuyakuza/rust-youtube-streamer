## Issue 1 — stderr is not captured (often returned empty)

### Evidence (exact commands + observed results)

| Command (via `alpine-vm_vm_run_command`) | Exit code | Observed output |
|---|---|---|
| `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust cargo fmt --check` (before toolchain fix; fails against wrong-style file) | 1 | stdout AND stderr both returned EMPTY (a failing `fmt --check` must print a diff to stdout) |
| `docker run --rm rust:1.82 rustfmt --version` (component absent) | 1 | both channels EMPTY ("error: component `rustfmt` is missing" expected on stderr) |
| `docker run --rm … rust:1.82 cargo check --locked` (first attempt, mmap crash) | 101 | both channels EMPTY (rustc error text expected on stderr) |
| `docker compose run --rm rust cargo check --locked` (healthy run) | 0 | EMPTY expected `Finished …` line lives on stderr |
| `docker ps`, `ls`, `cargo --version`, `cargo test` | 0 | stdout captured correctly |

### Conclusion

The tool reliably propagates the **exit code**, but **stderr is missing from the response in most/all cases** (and occasionally stdout too). Exit-zero and non-zero commands that print only to stderr appear as fully silent, which makes remote diagnosis impossible without re-running with different shapes (our workaround: component inclusion checks, `ls` of toolchain dirs).

### Proposed solutions (pick, implement, verify)

1. **Capture both SSH exec channels fully**: `stdout`, `stderr`, and `exitCode` as three explicit, always-present fields — including explicit "<empty>" content, so a caller can distinguish "stream empty" from "field missing/unreliable".
2. **Add a merged `combined_output` convenience field** (stdout + stderr interleaved in stream order) — consumers of build-tool output mostly want both; keeps the composite usable even if one channel is empty.
3. **Bound + truncate honestly**: define a max captured size per channel; when truncated, say so in the result (never silently swallow; never drop everything because one channel overflowed).
4. **Verify no TTY/PTY mismatch**: if stdout captures fine but stderr doesn't, check whether the SSH exec channel for stderr is being drained/read to completion before command end, or whether a PTY is requested and discarding the stderr channel.
5. **Regression tests** with stderr-only and mixed-output commands, e.g.:
   - `sh -c "echo err 1>&2; exit 3"` → expect stderr `err`, exit 3
   - `sh -c "echo out; echo err 1>&2"` → expect both channels non-empty
   - long-output command near the size bound → expect truncation notice, not empty.

## Issue 2 — vboxsf mmap silent build failures (context for the MCP, not a bug in it)

### Evidence

- First `cargo check` writing build artifacts (`target/`) onto the vboxsf shared folder: 0-byte `rmeta`, exit 101, zero output (see Issue 1 — the error text would have been on stderr).
- Plain sequential writes to the mount work fine (e.g., `Cargo.lock` creation). Memory-mapped writes do not.
- Resolved in this repo by redirecting `CARGO_TARGET_DIR` to a Docker named volume (`rust-streamer-target:/rust-streamer-target`) — nothing but source files and the tracked `Cargo.lock` live on the mount now.

### Proposed actions for the MCP project

- With Issue 1 fixed, this class of failure becomes diagnosable (rustc prints its real error). No MCP change strictly required.
- Optional nicety: if `vm_status` were extended to report mount details (e.g., vboxsf vs virtiofs, mount path), agents could warn proactively. LOW priority.

## Issue 3 — composite commands friction (minor)

### Evidence

- Allowlisted prefixes force `docker …`/`sh …` starts; chained commands (`&&`) are prohibited by agent rules, so a combined-stream run had to be phrased as a single `sh -c "… 2>&1"` string inside the container.

### Proposed actions

- Keep the prefix guard. Explicitly document that `sh -c "<single command string>"` is the sanctioned way to compose (quoting rules, no multi-command chains in one string unless the caller's plan allows it).
- Optional: document the recommended result-interpretation contract: "exit code authoritative; output informational; trailing note when capture is empty".
