# TODO — Phase 01: Configuration and Application Skeleton

## Objective

Turn the Phase 00 build baseline into the first real application foundation: load and validate external JSON configuration, establish the `auth` and `run` command interface, initialize structured logging, and connect startup through a small application orchestration layer.

This phase must leave the application buildable and testable without YouTube credentials, network access, or FFmpeg. It does not implement authentication or streaming behavior; those belong to later phases.

Before implementation, re-read the current repository and the project-info files. Phase 00 is complete. The repository has a minimal Rust 2021 executable, a pinned Docker toolchain for local checks through the Alpine VM, and `scripts/dev-checks.sh`. Keep using that established Docker/MCP workflow for all Cargo commands; do not assume Rust or Cargo is installed in the implementation-agent host.

Follow `AGENTS.md`, `.agent/WORKFLOWS.md`, `.agent/RULES.md`, `.kilo/commands/critical-workflow.md`, and `.agent/project-structure.md`. The project brief is the source of truth.

## Tasks

### 1. Implement the Configuration Module [DONE]

- Add the first real implementation under `src/config/`, following the current project structure map and the brief's configuration requirements.
- Define strongly typed configuration structs for the required MVP settings:
  - YouTube broadcast metadata: title, description, and privacy status.
  - Video: width, height, FPS, and pixel format.
  - Renderer: font path, font size, line height, four margins, text color, and background color.
  - Chat: log file path.
  - FFmpeg: executable path, video codec, preset, and bitrate.
- Use Serde and `serde_json` for JSON deserialization. Choose only additional dependencies that are justified for validation or error reporting; document the rationale in the completion report.
- Include `config/config.example.json` with safe, non-secret example values consistent with the brief. Do not create or commit `config/config.json`.
- Implement a clear configuration-loading API that accepts an explicit path instead of relying on a hardcoded current working directory.
- Validate configuration before application startup proceeds. At minimum:
  - Video width, height, and FPS must be positive.
  - The MVP pixel format must be `rgb24`; reject unsupported values rather than silently substituting one.
  - Font size and line height must be positive.
  - Margins must be non-negative and must leave usable rendering space; the vertical layout must allow at least one line.
  - Required strings and paths must not be empty or whitespace-only.
  - Privacy status must be one of the supported YouTube values `private`, `public`, or `unlisted`.
  - FFmpeg codec, preset, and bitrate must be present and non-empty.
- Do not require that the configured font or FFmpeg executable already exists during generic deserialization. File existence and process-start validation belong to the component that uses those resources; configuration validation may check path syntax and non-empty values.
- Use typed, actionable errors that identify the configuration file or field and explain the invalid value. Avoid panics for expected file, JSON, and validation errors.
- Keep the visible-message capacity derived from video height, vertical margins, and line height when that calculation is introduced; do not add a configurable `max_messages` field.
- Add unit tests for valid configuration, missing/unreadable configuration file, malformed JSON, missing required fields, invalid dimensions/FPS, unsupported pixel format, invalid margins/line geometry, invalid privacy status, and empty required values. Tests must use temporary files/directories and must not depend on a developer's real config.

### 2. Establish the Application and CLI Skeleton [DONE]

- Add the minimal module files and implementation needed under `src/app/`; update `src/main.rs` to delegate to this application layer instead of printing the Phase 00 placeholder.
- Provide two documented commands:
  - `rust-youtube-streamer-service auth`
  - `rust-youtube-streamer-service run`
- Use a maintained, conventional CLI parser if justified, or a small standard-library parser if it can support the interface cleanly without brittle ad-hoc parsing. Make the choice explicit and keep the CLI surface minimal.
- Support an explicit configuration-path option (for example, `--config <path>`) for both commands. Define and test the default path as `config/config.json`; the example config must not be loaded implicitly as a live configuration.
- Invalid arguments, unknown commands, missing config, or invalid config must produce a concise actionable error and a non-zero exit code.
- Both commands must load and validate configuration and initialize the application's logging before handing off to their mode handler.
- Since OAuth is not implemented in this phase, `auth` must report clearly that authentication is not implemented yet and exit non-zero; it must not pretend to authorize or persist credentials.
- Since streaming is not implemented in this phase, `run` must report clearly that the runtime pipeline is not implemented yet and exit non-zero after successful configuration validation. It must not create YouTube resources or start FFmpeg.
- Keep command dispatch and configuration loading testable without launching real external processes or requiring secrets.

### 3. Establish Structured Logging and Error Boundaries

- Initialize structured application logging once at startup, using a maintained logging stack such as `tracing` and `tracing-subscriber` if that remains the simplest suitable option.
- Allow the log filter to be configured through the conventional `RUST_LOG` environment variable, with a safe documented default if it is unset or invalid.
- Log the selected command and high-level startup/validation outcomes. Never log secrets, tokens, stream keys, or the full contents of the configuration file.
- Use explicit error propagation from configuration and application setup to the process entry point. Convert fatal startup failures to a non-zero process exit code without duplicating the same error at multiple layers.
- Do not add Tokio yet unless a concrete requirement in this phase needs asynchronous execution. Do not preemptively implement task supervision, signal handling, or YouTube lifecycle states.

## Dependencies and Design Constraints

- Follow the project's dependency policy: select maintained crates with suitable licenses, use Cargo's normal lockfile workflow, and avoid unnecessary frameworks.
- Keep the modular-monolith boundaries. The config module must not depend on YouTube clients, the renderer, or FFmpeg.
- The application layer may coordinate config loading, logging, and command dispatch, but must not contain future YouTube API, chat, rendering, or process-pipeline implementations.
- Do not use the rejected `google-youtube3` crate.
- Do not add empty feature modules for OAuth, broadcast, chat, renderer, or streaming just to fill the target tree.
- Keep the default broadcast privacy as `unlisted` in the example configuration.
- Do not add game logic, sprites, audio, chat commands, or moderation.
- The executable is launched directly by a normal user. Do not add Windows/Linux service registration, an installer, administrator elevation, or service-wrapper behavior.
- Do not install, download, bundle, or configure FFmpeg system-wide.
- Do not add CI or deployment-container changes. Preserve the current Docker setup solely for local development checks.
- Do not claim native Windows/Linux runtime validation based only on container checks.
