# TODO — Phase 01.1: Reproducible Linux Build Artifact

## Objective

Add a documented, repeatable way to build the current Rust executable in release mode and leave the resulting Linux executable in the repository-root `dist/` directory. This is a developer build-artifact workflow, separate from the existing fast validation workflow in `scripts/dev-checks.sh`.

The implementation must use the existing pinned Docker Compose Rust toolchain through the Alpine VM MCP. It must clearly identify the artifact as a Linux executable built inside the Linux container; it must not claim to produce a Windows executable or validate native Windows execution.

## Current Repository Baseline

Phase 00, Phase 00.1 (development-check script), and Phase 01 (configuration and application skeleton) are complete and merged into `main`. The application currently supports config validation and placeholder `auth`/`run` modes; there is not yet an OAuth or streaming pipeline.

Before implementation, re-read the live repository and project-info files, especially `AGENTS.md`, `.agent/WORKFLOWS.md`, `.agent/RULES.md`, `.kilo/commands/critical-workflow.md`, `.agent/project-structure.md`, `.agent/project-info/brief.md`, `.agent/project-info/context.md`, `Dockerfile`, `docker-compose.yml`, `scripts/dev-checks.sh`, `README.md`, and `.gitignore`.

All Cargo commands must continue to run through the existing Alpine VM MCP and Compose service. Do not assume Rust/Cargo exists on the implementation-agent host.

## Tasks

### 1. Implement a Release Build Script

- Create `scripts/build-linux.sh` as a small POSIX `sh` script intended to run inside the existing Compose `rust` service with the working directory at `/rust-youtube-streamer`.
- The script must run the release build using the tracked lockfile (equivalent to `cargo build --release --locked`).
- After a successful build, copy the expected executable from `$CARGO_TARGET_DIR/release/rust-youtube-streamer-service` into `dist/rust-youtube-streamer-service` on the mounted project directory. Resolve paths from the documented Compose working directory and current `CARGO_TARGET_DIR`; fail with a clear error if required environment/paths or the compiled executable are missing.
- Create `dist/` if needed. This is the explicitly approved exception to the standing rule that containers must not generate files in the project root: only the requested final build artifact may be written under the root-level, gitignored `dist/`. Intermediate Cargo artifacts must remain in the existing named Docker volume.
- The script must fail non-zero if the Cargo build or artifact copy fails; it must not report success before the final file exists and is non-empty.
- Print clear start/result messages and the exact output path. Do not suppress Cargo diagnostics.
- Do not modify source files, run `cargo fmt` automatically, write logs elsewhere, or delete unrelated files in `dist/`.
- Keep the script maintainable and consistent with the project's shell-script conventions. No additional shell framework or dependency.

### 2. Define Artifact Semantics and Safe Ignore Rules

- Confirm `dist/` is ignored by the existing `.gitignore` rule; adjust the rule only if needed, without unignoring any other build artifacts.
- Ensure generated binaries under `dist/` are not staged or committed.
- Document that this script produces a **Linux release executable** using the pinned Linux Rust container, not a Windows `.exe`.
- Explain that the named Docker volume stores Cargo's intermediate/release output, while the final copied artifact persists in the shared repository's `dist/` directory.
- Do not remove the named volume, prune Docker resources, or delete existing build outputs as part of the workflow.

### 3. Document the Build Workflow

- Create `docs/build.md` with a concise table of contents and clear prerequisites, build command, expected output path, behavior/failure semantics, and artifact platform limitations.
- The documented invocation must use the established Compose service, for example:
  `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/build-linux.sh`
- Distinguish the release artifact workflow from `scripts/dev-checks.sh`: checks validate formatting/types/tests/lints; the build script generates a distributable release executable.
- Explain how to rebuild/overwrite the generated artifact by rerunning the script and that the artifact is disposable/re-creatable.
- Explicitly state that a successful Linux container build does not prove native Windows/Linux runtime behavior, does not create a Windows executable, and does not mean the application streaming pipeline is implemented.
- Link `docs/build.md` from the README with a short summary. Keep unrelated README sections intact.
- Update `.agent/project-structure.md` with the script and documentation paths and the ignored `dist/` output.
- Update `.agent/project-info/context.md` with the actual implementation, exact build/check results, output path, platform caveat, and next phase.
