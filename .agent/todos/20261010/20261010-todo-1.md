# TODO — Phase 01.2: Reproducible Windows Executable Build

## Objective

Add a repeatable Docker-based cross-compilation workflow that produces a Windows x86-64 executable for local testing on Windows, while preserving the existing Linux build and development-check workflows.

The implementation agent must use the existing Alpine VM MCP and Docker Compose environment. Do not require Rust or Cargo to be installed on the Windows host. The resulting executable must be written to the gitignored repository-root `dist/` directory so it can be accessed from the shared project folder.

## Current Repository Baseline

Phase 01.1 is complete and has a tracked report at `.agent/reports/20261009-phase-01-1-build-artifact-workflow.md`. It provides:
- `scripts/build-linux.sh`, which builds the Linux release executable into `dist/rust-youtube-streamer-service`.
- `scripts/dev-checks.sh`, which runs formatting, check, tests and clippy in the pinned `rust:1.82` Docker Compose service.
- `docker-compose.yml`, which mounts the project at `/rust-youtube-streamer` and redirects Cargo output to the named volume `rust-streamer-target`.
- `dist/` already gitignored.

Before implementation, re-read the live repository and the applicable project/agent instructions, especially `AGENTS.md`, `.agent/WORKFLOWS.md`, `.agent/RULES.md`, `.kilo/commands/critical-workflow.md`, `.agent/project-structure.md`, all required project-info files, `Cargo.toml`, `Cargo.lock`, `Dockerfile`, `docker-compose.yml`, `scripts/build-linux.sh`, `scripts/dev-checks.sh`, `docs/build.md`, `README.md`, and `.gitignore`.

## Tasks

### 1. Add Windows GNU Cross-Compilation Support [DONE]

- Target 64-bit Windows using Rust target `x86_64-pc-windows-gnu`. This is the selected cross-compilation route because the build runs in a Linux container; do not attempt to set up the MSVC toolchain in this phase.
- Extend the existing pinned Rust container build environment with the minimum required Windows GNU cross-linker/toolchain packages, using the package manager appropriate to the actual base image. Add the Rust target to the container build environment. Keep Rust pinned to the existing `1.82` baseline unless a demonstrated blocker requires a documented decision to change it.
- Keep the existing Linux target and current Compose service behavior working. Do not replace the Linux workflow with a Windows-only image.
- Use Cargo's target-specific build invocation with the tracked lockfile (equivalent to `cargo build --release --locked --target x86_64-pc-windows-gnu`).
- Keep all intermediate Cargo artifacts in the existing named Docker volume via `CARGO_TARGET_DIR`; do not create a project-root `target/` directory.
- Avoid new Rust crate dependencies unless the existing source demonstrably requires them. Cross-compilation support should primarily be a toolchain/build configuration change.

### 2. Produce a Windows Artifact Safely [DONE]

- Add `scripts/build-windows.sh`, a POSIX `sh` script following the validation and error-reporting conventions of `scripts/build-linux.sh`.
- Require the documented Compose working directory `/rust-youtube-streamer` and a non-empty `CARGO_TARGET_DIR`; report clear errors and return non-zero for precondition, Cargo, linker, copy, or output-verification failures.
- Build the release target with `--locked`, then copy only the expected executable from `$CARGO_TARGET_DIR/x86_64-pc-windows-gnu/release/rust-youtube-streamer-service.exe` to `dist/windows/rust-youtube-streamer-service.exe`.
- Verify the source and final artifact exist and are non-empty before reporting success. Print the exact artifact path and size. Do not suppress Cargo diagnostics.
- Create `dist/windows/` if needed. The final executable under `dist/` is the explicitly approved root-level build-artifact exception; do not write generated intermediates or logs to the project root.
- Do not delete unrelated files under `dist/`, prune Docker resources, or alter the existing Linux artifact.
- Determine whether the selected GNU target's runtime requires MinGW DLLs on Windows. The output must be practically runnable on a standard 64-bit Windows environment: prefer static-linking compatible GNU runtime components when supported and verified; otherwise copy only the required redistributable runtime DLLs next to the `.exe` and document them. Do not bundle FFmpeg; it remains an independently installed external prerequisite. Do not assume or claim that a successful link alone proves the executable runs on Windows.

### 3. Document and Integrate the Workflow

- Create `docs/build-windows.md` with a table of contents if the document exceeds 100 lines, prerequisites, the exact Docker Compose command, output path, overwrite behavior, failure semantics, toolchain/target choice, and platform limitations.
- Document the standard command:
  `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/build-windows.sh`
- Clearly distinguish the three workflows:
  - `scripts/dev-checks.sh`: Linux-container formatting, checks, tests and clippy.
  - `scripts/build-linux.sh`: Linux release executable.
  - `scripts/build-windows.sh`: Windows x86-64 GNU release executable.
- Link the Windows guide from README and update `.agent/project-structure.md` and `.agent/project-info/context.md`.
- State that cross-compilation does not equal native Windows runtime validation. The actual `.exe` must be tested separately on Windows; report that validation as not run unless evidence from a Windows environment is supplied.
- Keep the app's platform model unchanged: normal user executable, no installer, no Windows service registration, no elevation. FFmpeg remains external and is not installed by this project.

### 4. Verify Both Build Paths and Save a Completion Report

- Through the Alpine VM MCP, run the documented Windows build command and record its exact exit status and observed output/artifact size.
- Re-run the existing Linux release build command to confirm the container/toolchain change did not regress it:
  `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/build-linux.sh`
- Run the standard development gate on the final tree:
  `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/dev-checks.sh`
- Confirm `dist/` remains ignored and neither output is tracked or staged. Keep any logs in the already gitignored `logs/checks/` location only if the existing script writes them there.
- Create a tracked completion report at `.agent/reports/20261010-phase-01-2-windows-build-workflow.md`. Include files created/changed; exact Docker/MCP commands and exit statuses; target/toolchain chosen; Windows and Linux build results; observed artifact path and size; runtime DLL handling; dev-check results; gitignore/tracking evidence; and all native Windows checks not run, with reasons. Never invent verification, outputs, sizes, or test results.
- Update this TODO's task markers and acceptance checklist only after the actual steps and required verification have completed. Do not rename it with `-DONE` until the Critical Workflow completion steps are finished.

## Constraints and Out of Scope

- No renderer/chat-store implementation (Phase 02), OAuth, YouTube API, FFmpeg process integration, or streaming behavior.
- No MSVC cross-toolchain, 32-bit Windows, macOS target, multi-platform matrix, installer, service registration, elevation, CI pipeline, or host-side Rust installation.
- Do not change application source unless the cross-build exposes a demonstrated source portability issue; stop and document it before broadening scope.
- Do not change dependency versions or upgrade Rust without a documented blocker and explicit review.
- Do not treat Linux container tests as native Windows runtime validation.
- Preserve the existing Linux build and development-check commands and the named-volume policy for intermediate artifacts.
