## Tasks

### 1. Chat Message Model and ChatStore

- Implement an application-level chat message model under src/chat/ without importing YouTube API types.
- Keep the model sufficient for display (username: message) and future internal correctness (message ID and timestamp when available). Keep optional API metadata optional and out of visible text.
- Implement ChatStore with a bounded in-memory FIFO queue, preferably VecDeque, containing only currently visible messages.
- Derive queue capacity with overflow-safe arithmetic using floor((height - top_margin - bottom_margin) / line_height). Validate that capacity is at least one; do not add a max_messages config value.
- On accepting a message, append its normalized log representation to the configured chat log and update the visible FIFO queue, evicting the oldest message when capacity is exceeded. Define clearly how I/O failures affect acceptance; avoid silent log loss or ambiguous queue/log state.
- Surface log path and I/O errors clearly. The log is append-only, independent of the transient queue, and must never be read to restore queue contents.
- Each new ChatStore starts with an empty queue. No historical replay, network, or YouTube behavior.
- Make file behavior testable with temporary directories/files.

### 2. RGB24 Text Renderer

- Implement a small renderer trait and concrete MVP renderer (e.g. TextRenderer) under src/renderer/, with typed errors for construction/rendering failures. Match brief §9.
- Input represents the complete visible multiline text. Renderer does not own message history, scrolling, queue capacity, YouTube state or FFmpeg process management.
- Render full frames at configured width/height. Each frame contains exactly width * height * 3 bytes in RGB24 order. Use checked arithmetic for byte sizes and return actionable errors for overflow or invalid allocations.
- Empty input yields a completely black frame. Non-empty input yields a black background with white text, in line order, using configured font, font size, line height and margins.
- Load the configured font explicitly; no silent fallback to an unspecified system font. Missing, unreadable or invalid fonts must produce clear, testable errors.
- Clip text at frame boundaries horizontally; do not wrap, dynamically resize fonts or implement additional truncation behavior. Respect left/top margins and line spacing. Never draw outside frame boundaries.
- Reject invalid rendering geometry without panics.
- Choose a maintained cross-platform font rasterization crate compatible with Rust 1.82 and Windows/Linux, or justify another approach. Update Cargo.toml and Cargo.lock only as needed. Prefer a portable crate-based solution that does not require platform-installed graphics libraries.
- Include a font asset only if redistribution license and provenance are documented. Otherwise document the operator-supplied font requirement and use a deterministic test fixture or a properly licensed repository font for tests.
- The current config includes text_color/background_color, while the brief's MVP rendering contract explicitly says white text on black. Do not silently change the public config contract. Clarify and test the chosen behavior; if schema/validation changes are necessary, update model, tests, example JSON and docs together.

## FFmpeg / YouTube Requirements for the Later Streaming Phase

The user's research must inform Phase 03 (FFmpeg Process and Local Video Pipeline), not expand this phase into streaming implementation. Current official YouTube encoder guidance:
- RTMP/RTMPS ingestion is supported; RTMPS is recommended. Use the actual ingestion endpoint supplied by YouTube, never a guessed URL.
- H.264 is supported; current guidance also lists H.265/HEVC and AV1. Keep libx264 as the initial compatibility default unless a later documented decision changes it.
- Keyframe interval: 2 seconds recommended, no more than 4 seconds. Derive GOP from FPS (30 FPS → 60 frames; 60 FPS → 120); do not hardcode 60 for every configuration.
- CBR is recommended. Appropriate bitrate depends on resolution, FPS and codec; Gemini's numbers are not universal. Preserve configurability and check official guidance again in Phase 03.
- AAC or MP3 are listed audio codecs for RTMP/RTMPS. The project brief explicitly says audio is outside MVP scope. Do not add silent audio or claim YouTube requires it without verified official support and an explicit scope decision. Phase 03 must decide/document how a video-only stream is handled while respecting the brief's audio non-goal.
- FLV is the FFmpeg output container for the RTMP/RTMPS route. Destination must use the valid ingestion endpoint and stream key supplied by the YouTube API flow; treat both as secrets and never log them.
- FFmpeg raw-video input must match renderer RGB24 bytes, configured dimensions and FPS. Output encoding/pixel format (commonly yuv420p for H.264 SDR) must be selected and validated in Phase 03.
- Official sources to re-check in Phase 03: https://support.google.com/youtube/answer/2853702?hl=en and https://developers.google.com/youtube/v3/live/guides/rtmps-ingestion. These notes are planning guidance, not a substitute for fresh verification.
