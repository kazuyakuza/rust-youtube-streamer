# TODO — Phase 03: FFmpeg Process and Local Video Pipeline

## Objective

Connect the Phase 02 chat store and RGB24 renderer to a real FFmpeg subprocess and produce a finalized local MP4 video. This phase proves the continuous frame-generation and encoding pipeline without depending on YouTube credentials, YouTube APIs, a live broadcast, or live chat.

Add a dedicated `demo` command that injects predefined messages at deterministic intervals so the resulting video visibly demonstrates the renderer and message lifecycle. Keep `run` as the future production entry point: it must not prompt for input or implement interactive message entry in this phase.

Phases 00, 00.1, 01, 01.1, 01.2 and 02 are complete. Phase 02 implemented `ChatStore` and the RGB24 text renderer, but neither is wired into `app::run`; `auth` and `run` remain placeholders that exit 3 after configuration validation.

## Tasks

### 1. FFmpeg Process Wrapper and Local MP4 Output

- Implement a `streaming` module that starts FFmpeg as an external child process, pipes raw RGB24 frames through its standard input, closes stdin to signal end-of-input, waits for process completion, and reports non-zero exits or process I/O failures as actionable typed errors.
- Construct FFmpeg arguments without invoking a shell. Supply raw-video input format `rgb24`, configured video size, configured frame rate, and the project's configured video codec, preset and bitrate. Choose and document compatible output encoding/container settings for a local MP4 file; use a broadly compatible H.264/MP4 configuration unless repository constraints or verified compatibility require otherwise.
- Configure output so the MP4 is finalized when the process exits normally. Do not report success until FFmpeg has exited successfully and the output file has been finalized.
- Keep stdout/stderr handling from causing a pipe deadlock. Do not log secrets or dump arbitrary sensitive process arguments. Include useful process diagnostics without leaking credentials (there should be no YouTube credentials in this phase).
- Resolve output directory `videos/` relative to the executable's directory, not the process current working directory. Create it if needed and return a clear error if it cannot be created or written.
- Use distinct timestamped filenames for demo and production pipeline outputs, such as `demo-YYYYMMDD-HHMMSS.mp4` and `session-YYYYMMDD-HHMMSS.mp4`. Prevent accidental overwrite if two runs occur within the same timestamp resolution; use a collision-safe suffix or another deterministic, tested strategy.
- Do not commit generated MP4 files. Ensure the repository's ignore rules cover local video output as appropriate, without broadening ignore rules for unrelated files.
- Keep FFmpeg process management independent of YouTube API types, chat message semantics and rendering details. Define a small interface for sending complete frames and finishing the process.

### 2. Continuous Local Frame Pipeline

- Wire the Phase 02 renderer and ChatStore into the application-level orchestration and the FFmpeg frame writer.
- Emit frames continuously at the configured FPS, including before the first message and during intervals when no new message arrives. The empty initial frame must show the configured black background.
- For each frame, render the complete currently visible text from ChatStore and write exactly one full RGB24 frame to FFmpeg stdin. Handle short writes and broken pipes correctly; never silently drop or truncate frame bytes.
- Respect the renderer's configured width, height, font, margins, line height and color behavior. Do not add wrapping, scrolling changes, game logic or a screenshot path.
- Keep the frame loop paced against the configured FPS rather than generating frames as fast as the CPU allows. Avoid accumulating unbounded timing drift or an unbounded frame/message queue.
- Ensure normal completion stops frame production, closes FFmpeg stdin, waits for process completion, and surfaces any FFmpeg failure. Do not claim the MP4 is valid merely because a file was created.
- Handle Ctrl+C as a shutdown request where cross-platform support permits, using a minimal approach compatible with Windows and Linux. If graceful interruption cannot be guaranteed on a target, document the limitation instead of claiming it works.

### 3. Dedicated `demo` Command

- Add `demo` to the CLI parser and help/usage text without breaking the existing `auth`, `run`, `--config` ordering rules or existing exit-code contracts.
- `demo` must load and validate configuration through the existing startup funnel, then run a local-only demonstration. It must not authenticate with YouTube, create YouTube resources, connect to a chat API, or transmit to YouTube.
- Use a small fixed, documented set of predefined chat messages with deterministic timing intervals. Feed these messages through ChatStore so they are logged and rendered by the same path as future real chat messages.
- Keep the demo running long enough for messages to appear and remain visible for multiple frames; allow the configured FIFO capacity to evict older messages naturally. Finish automatically after the planned demo timeline and finalize the MP4.
- Write the result under `videos/` beside the executable with a `demo-` filename prefix. Print/log the final output path only after FFmpeg exits successfully.
- The demo's message sequence and schedule must be testable without depending on real-time sleeps where practical. Use an injectable clock/scheduler seam or isolate the schedule data so unit tests can verify it deterministically.
- Do not make `demo` a screenshot command or a substitute for a future interactive mode.

### 4. Production `run` Mode Boundary

- Replace the `run` placeholder only to the extent supported by this phase's production boundary. It must not accept manually typed messages, read stdin as chat input, or expose a keyboard menu/hotkeys.
- Since OAuth, broadcast lifecycle, ingestion URL acquisition and YouTube chat integration are not implemented in this phase, `run` must fail clearly before pretending to stream to YouTube. Do not silently substitute local demo behavior for production `run`.
- If useful, structure reusable local frame-pipeline orchestration so a future production mode can supply real chat messages and an eventual YouTube output target without rewriting FFmpeg/frame generation. Clearly separate local-file output from future RTMPS output.
- Keep `auth` as its existing placeholder. Do not claim YouTube authentication, live chat, broadcast creation or live streaming has been implemented.
