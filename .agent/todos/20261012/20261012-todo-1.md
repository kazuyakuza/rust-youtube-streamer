# Phase 04 — OAuth 2.0 and Credential Management

## Objective

Implement the `auth` command and a reusable YouTube OAuth credential layer. This phase is strictly limited to user authorization, token exchange/refresh, safe credential persistence, and verification that the resulting authorization has the required YouTube scope/access.

The deliverable is a working first-time authorization flow that stores credentials for later unattended use, plus a reusable credential-loading/refresh path for future production `run` startup.

## Scope and Boundaries

- Implement OAuth 2.0 for a Google-installed application using a maintained Rust OAuth library where practical; evaluate dependencies and their maintenance, license, cross-platform support, and compatibility with the existing Rust 2021 toolchain before selecting them.
- Follow Google's currently supported installed-application flow. Prefer a loopback redirect/callback handled locally by the application when supported by Google's current requirements; do not require the user to manually paste access or refresh tokens.
- Load OAuth client configuration from an explicit, documented, configurable path. Keep OAuth client configuration distinct from the user's issued token/credential file.
- Persist only the token/credential data required for future use. Protect the credential file with restrictive permissions on platforms that support them, and document platform limitations without claiming encryption when none exists.
- Support loading stored credentials and refreshing expired access tokens when a valid refresh token is available. Persist refreshed token data safely.
- Verify the resulting credentials against the minimum YouTube API permission/scope needed for the next integration phases. Research and document the exact required scope using current official Google/YouTube documentation; do not request broad scopes without justification.
- Wire the existing `auth` CLI mode into this implementation, preserving CLI syntax and existing exit-code contracts unless a justified, documented change is required.
- Keep OAuth and credential handling isolated under `src/youtube/` (or a small clearly justified submodule) with typed errors and testable boundaries. Do not couple authentication to rendering, ChatStore, FFmpeg, or demo scheduling.
- Add tests for parsing/configuration, callback/error cases, token response handling, refresh behavior, persistence, permission failures, and secret-redaction guarantees. Prefer deterministic local fakes/mocks; automated tests must not require a real Google account or network access.
- Update configuration example/schema and relevant README/development/authentication documentation, project structure, project-info context, and a tracked completion report to reflect the actual implementation and evidence.
- Run the standard Docker-based development checks and rebuild both Linux and Windows release artifacts. Record exact commands and results; distinguish cross-compilation from native runtime testing.

## Explicitly Out of Scope

- Creating, listing, binding, transitioning, or otherwise managing YouTube Live broadcasts.
- Retrieving or using an RTMPS ingestion URL or stream key.
- Starting FFmpeg in production mode or transmitting any video to YouTube.
- Connecting to YouTube Live Chat or processing chat messages.
- Changing the `demo` pipeline, frame renderer, ChatStore, or local MP4 behavior.
- Manual token entry, stdin chat input, interactive menus, keyboard controls, audio generation, screenshots, or game logic.
- Logging client secrets, access tokens, refresh tokens, authorization codes, or other sensitive OAuth responses.
- Claiming native Windows/Linux runtime validation unless performed and recorded.

## Tasks

### 1. OAuth Design and Dependency Selection [DONE]

- Read the current project brief, tech constraints, CLI/configuration/error contracts, and Phase 03 completion report before changing code.
- Research Google's current official installed-application OAuth guidance, loopback redirect requirements, token endpoint behavior, refresh-token semantics, and the minimal YouTube API scope required for the subsequent phases.
- Evaluate maintained Rust OAuth and HTTP crates; document the selected approach and why it fits Windows/Linux and the project's existing toolchain.
- Define typed interfaces/errors for OAuth client configuration, authorization, token exchange/refresh, credential persistence, and authorization verification. Keep these boundaries mockable.
- Do not implement broadcast, ingestion, or chat functionality as part of this task.

### 2. OAuth Configuration and Credential Storage [DONE]

- Add the smallest justified configuration model for the OAuth client configuration path and persisted credential path, with defaults or explicit CLI/config behavior consistent with existing conventions.
- Update `config/config.example.json`, validation, tests, and documentation as required. Never load the example file implicitly as real configuration.
- Keep OAuth client secrets and token material out of source control. Preserve and verify applicable `.gitignore` rules.
- Write credentials atomically where practical so interruption does not leave a truncated valid credential file; restrict file permissions where supported and test/document the behavior.
- Ensure errors and logs never expose secrets, tokens, authorization codes, or full token endpoint response bodies.

### 3. Implement the `auth` Command [DONE]

- Replace the current `auth` placeholder with the installed-application authorization-code flow.
- Load and validate the configured OAuth client data before opening the flow.
- Display the authorization URL in the console and guide the user through browser authorization. Use the supported local callback mechanism and validate state to protect against cross-site request forgery; bind only to a loopback interface and shut the callback listener down after completion or failure.
- Exchange the returned authorization code for tokens, handle OAuth/provider errors with actionable but redacted diagnostics, and persist credentials securely.
- Verify authorization with the minimum required YouTube API permission/scope and return a clear non-zero exit code if authorization is missing, revoked, or insufficient.
- Exit after successful verification; do not leave background listeners or tasks running.
- Preserve the existing non-interactive `run` placeholder and local-only `demo` behavior.

### 4. Credential Loading, Refresh, and Verification

- Implement a reusable credential service for later production startup: load stored credentials, determine whether access-token refresh is required, refresh using a stored refresh token when possible, and persist updated token data.
- Handle absent, malformed, unreadable, expired/unrefreshable, revoked, and insufficient-scope credentials with distinct actionable errors.
- Verify the effective authorization through a minimal YouTube API request appropriate to the selected scope; avoid adding broadcast operations.
- Ensure refresh and verification logic can be unit-tested without live Google credentials or network access.
- Document that initial authorization requires user interaction and that future unattended operation depends on the issued refresh credentials and Google's current OAuth policies.

### 5. Tests, Documentation, and Completion Evidence

- Add focused unit tests for OAuth config validation, state/callback validation, successful and failed token exchange, refresh success/failure, atomic credential persistence, permission restrictions, and redacted diagnostics.
- Add integration tests around local fake HTTP/callback boundaries where feasible. No automated test may require a real Google account, live OAuth client secret, or network access.
- Run `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/dev-checks.sh`.
- Rebuild Linux: `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/build-linux.sh`.
- Rebuild Windows: `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/build-windows.sh`.
- Update README and relevant authentication/development documentation, `.agent/project-structure.md`, and `.agent/project-info/context.md`.
- Create a tracked report under `.agent/reports/` with dependency rationale, changed files, exact commands/exit statuses, tests, builds, security review, manual checks actually performed, and known limitations.
- Confirm no token, secret, authorization code, real credentials file, or other secret material was added to Git.

## Acceptance Criteria

- [ ] `auth` performs a real Google OAuth 2.0 installed-application flow and no longer returns the not-implemented exit code.
- [ ] The user can authorize through a browser and local callback without manually copying/pasting OAuth tokens.
- [ ] OAuth state is validated; callback binding is loopback-only; temporary listener resources are closed on success and failure.
- [ ] OAuth client configuration and issued credentials are separate, configurable files/paths with clear documentation.
- [ ] Credentials are persisted safely and atomically where practical; restrictive file permissions are applied where supported and limitations are documented.
- [ ] Access tokens can be refreshed from stored refresh credentials, and refreshed credentials are persisted.
- [ ] The resulting credentials are verified against the minimum documented YouTube API scope/permission required by subsequent phases.
- [ ] Missing, malformed, revoked, expired/unrefreshable, or insufficient credentials produce clear non-zero failures without leaking secrets.
- [ ] Automated tests cover success, failure, callback/state validation, refresh, persistence, permission, and redaction paths without real Google credentials or network access.
- [ ] `demo` behavior is unchanged, and `run` remains a non-interactive placeholder; no broadcast, RTMPS, FFmpeg production streaming, or Live Chat integration is added.
- [ ] Docker-based dev checks pass and both release artifacts are rebuilt, or exact blockers are recorded without claiming success.
- [ ] Documentation, project structure, project context, and completion report accurately describe implementation and verification.
- [ ] No credentials, tokens, authorization codes, client secrets, or generated local videos are committed.
