# Phase 05 — Production YouTube Live Runtime

## Objective

Implement the production `run` path that consumes the Phase 04 OAuth credential service, creates and prepares a YouTube Live broadcast, obtains the RTMPS ingestion destination, and connects the existing chat → renderer → FFmpeg frame pipeline to YouTube Live Chat and the real YouTube stream.

At the end of this phase, an operator must be able to run the executable with valid configuration and previously authorized credentials, have it create a new broadcast with the configured metadata/privacy, start a continuous video stream through FFmpeg, and render incoming live chat messages into that stream. The `demo` command remains a local-only recording mode.

## Scope and Boundaries

- Implement the production behavior behind the existing `run` CLI command; remove its exit-3 placeholder only when the complete startup path is wired.
- Reuse Phase 04's credential service, token refresh, scope verification, redaction-safe types, and credential persistence. Do not duplicate OAuth or introduce a second credential format.
- Implement direct YouTube API calls behind the project's own `src/youtube/` interfaces; `google-youtube3` remains rejected per the project brief.
- Before implementing API behavior, check current official Google/YouTube documentation for required OAuth scopes, broadcast/stream resource fields, lifecycle transitions, ingestion URL semantics, RTMPS support, and Live Chat retrieval. Record the selected API operations and relevant failure mappings in the implementation plan/report.
- Create one new broadcast per `run` invocation using `youtube.broadcast.title`, `youtube.broadcast.description`, and `youtube.broadcast.privacy_status`. Do not add broadcast reuse, multi-broadcast support, or a dashboard.
- Create and bind the required live stream resource, obtain its ingestion server address and stream name/key from API responses, and pass the assembled RTMPS destination to FFmpeg without logging the URL/key or embedding it in diagnostic errors.
- Use the existing configured FFmpeg executable and video encoding settings. Preserve the current locked FFmpeg local-recording behavior unless an explicit, documented production output mode is added; never regress `demo` output behavior.
- Integrate incoming messages from the created broadcast's active Live Chat into the existing application-level chat model/store, then feed the existing renderer/pipeline. Keep YouTube-specific types inside `src/youtube/` and translate to application chat types at the boundary.
- Use the current supported Live Chat retrieval API after researching official guidance. Prefer a streaming/push mechanism if it is currently supported and appropriate; if the supported API requires polling, implement the documented continuation-token/poll-interval behavior with bounded waiting and rate-limit-aware errors. Do not assume an endpoint or protocol without verification.
- Use Tokio only if the selected YouTube chat/runtime integration requires it and the architecture benefit justifies it; document dependency choice and isolate async API/chat work from the synchronous frame renderer and FFmpeg pipe.
- Coordinate startup, broadcast readiness, chat retrieval, video frame generation, FFmpeg transmission, Ctrl+C, and cleanup with typed errors and deterministic shutdown ordering. Do not mark startup successful until the broadcast is in a streamable state and FFmpeg has started successfully.
- Ensure operational logs are useful but secret-safe: never log OAuth tokens, refresh tokens, client secrets, stream keys, full RTMPS URLs, authorization codes, or raw provider response bodies that may contain secrets.
- Add offline tests using injected API transports, fake Live Chat sources, and fake FFmpeg executables. Automated tests must not require a real Google account, live credentials, a real broadcast, or network access.
- Add an opt-in/manual end-to-end verification procedure for the user to test against a real YouTube account and broadcast. Do not claim live API or native platform success unless that test was actually run and recorded.
- Update docs, configuration examples/schema only when required, project structure/context, and a tracked Phase 05 completion report with exact test/build/manual-check evidence.

## Explicitly Out of Scope

- OAuth browser authorization flow changes, except bug fixes required to consume the Phase 04 credential service correctly.
- Game mechanics, commands, moderation, message authorization/filtering, sprites, animations, audio generation, or user input controls.
- Multiple concurrent broadcasts, resuming/reusing an existing broadcast, a web dashboard, distributed services, or generalized crash recovery.
- Replacing the renderer, chat store, frame format, or existing local `demo` timeline.
- Writing RTMPS transport or H.264 encoding in Rust; FFmpeg remains responsible for encoding and transport.
- Logging secrets for diagnostics or committing credentials, tokens, stream keys, local videos, or build artifacts.
- Claiming native Windows/Linux runtime validation from cross-compilation alone.

## Tasks

### 1. Official API Research and Runtime Design

- Read the current brief, architecture, tech and project context, the Phase 03 and Phase 04 completion reports, and the actual staged OAuth/credential-service interfaces before designing the runtime.
- Research current official Google/YouTube documentation for:
  - required scopes for broadcast and stream management plus Live Chat access;
  - broadcast and live-stream creation, binding, readiness/status fields, and legal lifecycle transitions;
  - RTMPS ingestion address and stream-name/key response fields and the exact FFmpeg destination format;
  - current supported Live Chat message retrieval method, message schema, continuation tokens or stream lifecycle, polling limits/intervals, and quota/rate-limit behavior;
  - failure cases for disabled Live Streaming, channel eligibility, authorization revocation, quota exhaustion, broadcast transition conflicts, and chat ending.
- Select the smallest viable maintained HTTP/API/chat dependencies. Do not add a broad generated API client without documenting why it is necessary.
- Define typed API models, transport interfaces, errors, and lifecycle state transitions. Keep API transport and Live Chat sources mockable/offline-testable.
- Document the chosen orchestration and shutdown sequence before implementation; preserve the renderer and streaming boundaries.

### 2. Broadcast and Ingestion Lifecycle

- Implement the YouTube API operations needed to create a live stream and a broadcast from the validated config, bind them, and inspect status until the API reports the required stream/broadcast readiness.
- Use only documented fields and legal state transitions. Handle processing delays with bounded waits, cancellable waits, and a typed timeout/readiness error; never spin continuously or wait forever.
- Extract the ingestion server address and stream name/key from the API response and construct the RTMPS output destination without logging it.
- Add typed, actionable failures for invalid metadata/privacy, missing API permissions, unsupported or disabled Live Streaming, quota/rate limits, HTTP/provider errors, invalid resource responses, and readiness timeouts. Redact response details where they may contain credentials or keys.
- Add tests for successful create/bind/readiness flows, out-of-order/invalid states, API errors, timeouts, malformed responses, and secret redaction using a fake transport.

### 3. Live Chat Source

- Implement a production Live Chat source using the current official supported retrieval mechanism identified in Task 1.
- Resolve the active live-chat identifier from the created broadcast; do not hardcode an identifier.
- Convert provider message IDs, author/display names, message text, and any required timestamp into the existing application-level chat message model. Do not leak YouTube-specific resource structs into the renderer or ChatStore.
- Handle empty chat, duplicate/replayed messages, continuation-token updates or streaming reconnects, ended/disabled chat, deleted/unavailable chat, transient network failures, permission errors, and rate limits according to the selected API contract.
- Ensure waits and retries are bounded/cancellable and respect documented polling intervals, quotas, or server-provided retry guidance. Avoid busy loops and unbounded message buffering.
- Keep the chat log separate from the visible bounded ChatStore, following the brief. Ensure chat log failures have an explicit typed policy and cannot silently corrupt frame rendering.
- Add deterministic offline tests for new messages, no messages, ordering/deduplication as required by the API, continuation/reconnect behavior, cancellation, provider errors, and secret-safe diagnostics.

### 4. Production `run` Orchestration and FFmpeg Output

- Replace the `run` exit-3 placeholder with production startup that loads and refreshes credentials using the existing Phase 04 credential service and verifies required permissions before creating YouTube resources.
- Orchestrate startup in an explicit order: credentials/authorization → broadcast and stream resources → readiness and RTMPS destination → FFmpeg start → chat source and frame pipeline. Refine this sequence only if official API constraints or the existing pipeline contract require it, and document why.
- Extend the streaming output abstraction minimally so the existing FFmpeg process can target the RTMPS destination for production while the local `demo` command continues writing collision-safe MP4 files. Preserve no-shell process spawning, stdout/stderr draining, frame-write errors, and child cleanup.
- Do not place the RTMPS URL or stream key in command logs, tracing fields, error text, panic messages, or debug output. Test redaction around spawn/exit failures.
- Connect the Live Chat source to the existing pipeline without blocking frame pacing. Keep the frame loop continuously producing frames when chat is empty.
- Handle Ctrl+C and fatal failures with a defined shutdown order: stop accepting/polling chat, request frame-loop stop, close FFmpeg stdin, wait for FFmpeg to exit, and report cleanup failures without masking the primary error. Stop or cancel in-progress API waits.
- Define and document what happens to the YouTube broadcast/stream resources on normal shutdown and startup failure. Do not automatically delete resources unless official API behavior and the chosen lifecycle policy explicitly justify it; avoid leaving a broadcast marked live when a clean transition out of live is available and required.
- Preserve the `auth` and `demo` behavior and stable CLI exit-code contracts; update the `run` usage text and tests to reflect the now-implemented mode.

### 5. Tests, Documentation, Builds, and Manual Verification Procedure

- Add unit and integration tests for API request/response mapping, broadcast lifecycle, RTMPS target redaction, chat ingestion, orchestration ordering, startup failures, shutdown, and preservation of the local demo.
- Use fake API transports, fake chat sources, and fake FFmpeg executables for automated tests; no automated test may contact Google or create a real broadcast.
- Run `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/dev-checks.sh`.
- Rebuild Linux: `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/build-linux.sh`.
- Rebuild Windows: `docker compose -f /rust-youtube-streamer/docker-compose.yml run --rm rust sh scripts/build-windows.sh`.
- Update README and relevant YouTube/streaming/configuration docs, `.agent/project-structure.md`, `.agent/project-info/tech.md`, and `.agent/project-info/context.md`.
- Create a tracked report under `.agent/reports/` documenting selected official API operations/scopes, dependencies, lifecycle/shutdown decisions, secret-redaction review, changed files, exact commands and exit statuses, test counts, artifact sizes, the manual verification procedure, checks actually performed, and limitations.
- Include a safe manual test plan that covers a real unlisted broadcast, actual video arrival, chat-message rendering, Ctrl+C shutdown, and confirmation of broadcast status afterward. The plan must remind the operator to keep tokens and stream keys private and distinguish user-run manual validation from automated/container checks.
- Confirm no real credentials, tokens, stream keys, RTMPS URLs, local MP4s, or build artifacts were committed.

## Acceptance Criteria

- [ ] `run` no longer returns exit 3 for the implemented production path and remains non-interactive.
- [ ] The Phase 04 credential service is reused for loading, refresh, permission verification, and redacted failures; OAuth is not duplicated.
- [ ] A new broadcast and live-stream resource are created from configured metadata/privacy, bound, and advanced/readiness-checked according to current official API requirements.
- [ ] The RTMPS ingestion destination is obtained from the API response and used by FFmpeg without exposing the stream key/URL in logs or errors.
- [ ] FFmpeg transmits configured continuous video to YouTube Live, including frames while chat is empty; the local `demo` command still generates a local MP4 with unchanged behavior.
- [ ] Live Chat messages are fetched using a currently supported official mechanism, mapped to the application chat model, logged separately, and rendered in the video.
- [ ] Polling/streaming waits, retries, readiness checks, cancellation, and shutdown are bounded and respect documented API limits.
- [ ] Typed errors cover auth/scope, API/quota, broadcast/stream state, ingestion, chat, FFmpeg, and shutdown failures with secret-safe diagnostics.
- [ ] Offline tests cover lifecycle success/failure, chat ingestion, orchestration, redaction, cancellation/shutdown, and demo regression without live Google access.
- [ ] Normal shutdown and startup-failure behavior for broadcast/stream resources is documented and tested where practical.
- [ ] Docker dev checks pass and both Linux and Windows release artifacts are rebuilt, or exact blockers are documented without claiming success.
- [ ] Documentation, project structure/context, and a tracked completion report accurately describe implementation and verification.
- [ ] No credentials, tokens, stream keys, RTMPS URLs, generated local videos, or build artifacts are committed.
