# Fix — `run` Fails With HTTP 411 (Length Required) at the Broadcast Bind Step

## Objective

The operator's native Windows `run` attempt (log `logs/run/20261022-033554.log`) aborted with
`error: YouTube rejected request (HTTP 411, reason 'unspecified')` right after
`stored authorization verified`, exiting 1. Fix the concrete YouTube Live API transport so the
run-path startup completes instead: the failing stage is O3 `liveBroadcasts.bind`, the ONLY
bodyless POST in the startup, sent through ureq's `call()` without a `Content-Length` header.
Google's API server requires `Content-Length` on POST and answers 411 Length Required.

Pre-analysis evidence (planner, 2026-10-22):

- `classify_api_error` maps 411 through its catch-all arm to `LiveApiError::ApiRejected { status: 411, reason: "unspecified" }`; `display.rs` renders exactly the observed line.
- The startup order is O1 insert stream (POST + JSON via `send_string` → `Content-Length` present), O2 insert broadcast (same), O3 bind (`LiveApiRequestSpec::posting` → `google_live_api_transport.request` → `pending.call()` — no body, no `Content-Length`); the verifier probe, O4/O5 lookups and readiness polls are GETs (never need `Content-Length`).
- The ~2.3 s window between "stored authorization verified" and the error is consistent with O1+O2 succeeding (quick round trips) and O3 being rejected; no bodyless-GET path can produce 411.
- Transport library: ureq 2.12.1 (locked). `Request::call()` on POST sends no `Content-Length` and no body bytes.

## Scope and Boundaries

- Change is confined to the bodyless-POST request form of the YouTube Live API transport (`src/youtube/api_request.rs` + `src/youtube/google_live_api_transport.rs`): a POST with NO request body must still transmit `Content-Length: 0` (HTTP-correct form of "do not provide a request body" per the liveBroadcasts.bind documentation); GET paths keep the current no-body `.call()` behavior.
- Regression coverage is offline loopback-only: pin the wire behavior a Google-like enforcing server needs (POST without a meaningful body but WITH `Content-Length: 0` accepted; POST without `Content-Length` rejected as the 411 class). No automated test ever contacts Google; the real-Google confirmation remains the operator's manual E2E procedure.
- Never log or surface the bind/platform secret material; redaction guarantees, shutdown order, resource-fate policy (never delete/transition), and the exit-code contract stay byte-stable beyond the error line this fix removes.
- FIX = semver PATCH bump (0.9.0 → 0.9.1) with refreshed tracked lockfile; both release artifacts rebuilt after the code change with `ls -l` sizes recorded.
- No candidate hardening items (ureq request-level timeout, bounded FFmpeg exit wait, hang watchdog, external supervisor) enter with this fix — they stay "candidates, not commitments" per the Phase-05 report addendum.

## Explicitly Out of Scope

- Live Chat ingestion/rendering (Phase 06).
- Any resilience-hardening implementation beyond this transport fix.
- Running `run`/`auth`/`demo` natively against Google (the agent never performs live E2E; operator-run only).
- Deleting or transitioning the operator's orphaned `ready` broadcast/stream left by the failed run — the app never deletes resources by recorded policy; the operator cleans them in YouTube Studio per `docs/production-run.md` §7 (planner communicates this to the operator; it is not code work).

## Tasks

- In the concrete transport's request engine, route the bodyless-POST form (O3 bind, the `posting` spec constructor) through a body-send path that transmits exactly zero body bytes WITH a `Content-Length: 0` header, verified against ureq 2.12.1 behavior (inspect the lockfile-pinned crate source inside the Compose container if documentation is ambiguous); the chosen mechanism must be pinned by a loopback test, not assumed.
- Keep `LiveApiMethod::Get` requests on the current bodyless `.call()` path; keep O1/O2 JSON-POST behavior and all five path builders, query encodings and request bodies byte-stable.
- Add/adjust loopback unit tests: (a) the bind-form POST arrives at the local test server with header `Content-Length: 0` and an empty body; (b) a POST arriving without `Content-Length` classifies as the observed 411 rejection shape, anchoring the incident; (c) existing pinned request-shape tests updated only where the wire form legitimately changed.
