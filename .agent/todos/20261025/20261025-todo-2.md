# Phase 06 — YouTube Live Chat Integration

## Objective

Connect the production `run` mode to the active YouTube Live Chat for the broadcast created by Phase 05. Retrieve incoming chat messages, translate them into the existing application-level chat model, append them to the existing chat log and bounded visible queue, and render them into the continuous video stream.

Phase 05's RTMPS/FFmpeg runtime remains the owner of video transmission and lifecycle. Phase 06 adds the real message source without rewriting that infrastructure. This also replaces the Phase 05 pure-black content with visible chat content when messages arrive; it does not promise that YouTube Studio's Stream Health assessment will clear for every chat pattern or broadcast.

## Current Repository Context

- Production `run` already authorizes through the Phase 04 credential service, creates and binds one broadcast/stream pair, starts FFmpeg toward RTMPS, confirms ingestion activity concurrently with the frame loop, and shuts down on Ctrl+C.
- The production frame pipeline is already shared between the chat model/store, renderer, and FFmpeg `FrameSink`. It accepts at most one due message per frame iteration.
- `src/app/run/source.rs` currently contains `ChatFreeSource`, which returns `None`; replace this production source with the Phase 06 YouTube-backed message source without changing `demo`'s deterministic schedule.
- `src/app/pipeline/source.rs` defines the synchronous `MessageSource` seam. Review its current contract and the Phase 05 seam-freeze comments before changing it. Preserve the renderer and streaming boundaries.
- `src/chat/model.rs` defines `ChatMessage` with normalized single-line author/text and optional message ID/timestamp metadata.
- `src/chat/store.rs` provides the bounded visible FIFO and append-only log. It appends to the log first and rejects the message if that append fails; preserve this contract.
- `src/youtube/` owns direct YouTube API calls and OAuth-related types. Keep YouTube-specific resource types inside this module.
- Phase 05's operator-supplied Windows runs eventually confirmed RTMPS ingestion and clean Ctrl+C shutdown. The known pure-black Stream Health limitation is documented in `docs/production-run.md`; do not regress the v0.11.1 stream-health and shutdown fixes.

## Scope and Boundaries

- Resolve the active broadcast's Live Chat identifier from the actual broadcast/API response; never hardcode an ID or assume every broadcast has chat enabled.
- Reuse the verified access token/transport and existing OAuth credential flow. Do not add a second OAuth flow or credential store.
- Before implementing the chat client, research current official Google/YouTube documentation and choose a currently supported Live Chat retrieval method. Evaluate the documented server-streaming `liveChatMessages.streamList` option against polling via `liveChatMessages.list`; do not assume either method's current availability, support status, transport requirements, or quota semantics.
- Implement the smallest direct API surface behind mockable interfaces in `src/youtube/`. Do not use `google-youtube3` and do not expose YouTube resource structs to `chat`, `renderer`, or `streaming`.
- Convert provider messages into `ChatMessage`, preserving the provider message ID and a normalized timestamp where the API supplies one. Render author and message text using the existing `Display` contract; provider metadata must not become visible text.
- Feed messages through the existing `MessageSource` → `ChatStore` → renderer → frame pipeline. Keep frames flowing continuously while chat is idle or empty.
- Preserve the separate append-only chat log and bounded visible queue. Do not restore old log records into the visible queue at startup.
- Preserve `demo` output, deterministic scheduling, FFmpeg local MP4 behavior, production RTMPS argument vectors, secret redaction, clean-stop behavior, and stable CLI exit-code contracts.
- Use Tokio or another async/runtime dependency only if official API requirements and the selected retrieval mechanism justify it. The current app and frame pipeline are synchronous; any concurrency bridge must be explicit, bounded, cancellable, and documented.
- Automated tests must remain offline: use fake transports/sources and loopback HTTP servers where useful. No test may use real credentials, contact Google, or create a broadcast.
- Document an operator-run manual verification against a real unlisted broadcast; do not claim live YouTube verification unless the operator actually performs and records it.

## Explicitly Out of Scope

- Changes to OAuth browser authorization, token persistence, broadcast creation/binding, RTMPS ingestion, FFmpeg encoding settings, or broadcast resource-fate policy except minimal integration fixes proven necessary.
- Game mechanics, chat commands, moderation, authorization/filtering, spam controls, user input, sprites, animations, audio production, or game state.
- Multiple concurrent broadcasts, chat replay/history restoration, web dashboards, distributed services, or automatic recovery from every crash.
- Switching the video renderer or replacing the existing `ChatStore` / `MessageSource` architecture wholesale.
- Promising that Stream Health warnings will clear: chat content addresses the known pure-black content limitation, but actual health classification remains YouTube-controlled and depends on the stream.

## Tasks

### 1. Official Live Chat API Research and Design

- Read `AGENTS.md`, `.agent/project-info/instructions.md`, `brief.md`, `context.md`, `architecture.md`, `tech.md`, `.agent/project-structure.md`, the Phase 05 completion report, `docs/production-run.md`, and the current implementation of the run, pipeline, chat, and YouTube modules.
- Research current official documentation for:
  - how to retrieve `liveChatId` for the broadcast created by Phase 05 and what response fields indicate chat is unavailable or disabled;
  - `liveChatMessages.streamList` support/status, protocol and client requirements, message payloads, reconnect behavior, and whether it is appropriate for this synchronous Rust service;
  - `liveChatMessages.list` fallback/alternative, `nextPageToken`, `pollingIntervalMillis`, empty responses, and correct continuation semantics;
  - current OAuth scopes, required authorization, API quota costs, rate limits, retry guidance, and relevant error reasons for both retrieval approaches;
  - message types, author details, timestamps, deletion/hidden/paid/system events, and which message kinds have user-visible text suitable for this prototype;
  - chat lifecycle behavior when the broadcast ends, chat is disabled, permissions are revoked, or the channel/broadcast is ineligible.
- Record official URLs, access dates, selected method and rejected alternatives, exact API calls/fields, quota calculations, dependencies and transport constraints in the implementation plan.
- Select a single production retrieval strategy and a deterministic fallback/error policy. Do not implement both methods unless official API evidence demonstrates that both are required.
- Define bounded message buffering, ordering/deduplication policy, retry/backoff limits, cancellation semantics, and typed error mapping before implementation.
- Decide whether the existing synchronous `MessageSource` trait can safely support the selected mechanism with a bounded worker/channel, or whether a minimal trait-contract change is necessary. Encode the choice and its effects on `demo` in the implementation plan.

### 2. YouTube Live Chat API Client and Message Mapping

- Add the required YouTube-specific models and mockable API/source interfaces under `src/youtube/`, following the existing direct-ureq transport and typed-error conventions.
- Reuse the authorized access token from Phase 05's credential/runtime setup. Do not log the token, authorization headers, raw response bodies, or sensitive provider data.
- Resolve the created broadcast's chat ID using documented fields. Handle absent chat ID or disabled/unavailable chat with an explicit typed error and an actionable diagnostic.
- Implement the selected documented retrieval operation with correct request parameters and response decoding.
- Map supported text-bearing chat messages to `ChatMessage`: normalized author/display name, normalized text, provider message ID, and timestamp converted to the model's expected epoch-second unit. Skip non-text/system events only according to a documented, tested policy; do not silently treat malformed message payloads as ordinary chat.
- Define behavior for empty responses, duplicate/replayed IDs, message ordering, continuation tokens or stream reconnects, deleted/hidden messages, unsupported event types, chat ended, permission failures, quota/rate limits, transient network failures, malformed responses, and cancellation.
- If polling is selected, honor the server-provided poll interval and continuation token; do not busy-loop, invent a fixed interval that overrides server guidance, or exceed documented quota behavior. If streaming is selected, honor protocol/reconnect semantics and bound all queued messages.
- Keep network waits/retries bounded and cancellable. Avoid unbounded buffers and avoid blocking the frame renderer or FFmpeg pipe on network I/O.
- Keep YouTube API types inside `src/youtube/`; the only cross-boundary output should be application-level `ChatMessage` values or the existing typed application error contract.

### 3. Production Run and Frame-Pipeline Integration

- Replace the Phase 05 `ChatFreeSource` with the real YouTube Live Chat source for `run`, wiring it to the broadcast's resolved chat ID and authorized API transport without creating another broadcast or altering Phase 05's resource lifecycle.
- Review the current `MessageSource::next_message` failure type. If chat retrieval introduces non-`ChatError` failures, make the smallest typed, backward-compatible contract change and update both production and test implementations; do not collapse provider/network failures into misleading chat-log errors.
- Keep `demo` on its existing deterministic source and preserve the local MP4 timeline/arguments exactly.
- Ensure the worker/source can be stopped by the existing Ctrl+C stop path and that blocked network operations or channel sends cannot prevent bounded shutdown.
- Preserve one-message-per-frame pacing and the current `ChatStore` log-first acceptance contract. A log-write failure must follow an explicit fatal error policy and must not be silently ignored.
- Keep the video frame loop continuous when no chat messages arrive, including during slow API responses, reconnects, or periods of empty chat.
- Define startup and shutdown order for the chat worker/source, frame loop, FFmpeg stdin EOF, FFmpeg wait, and any API connection. Ensure worker errors reach the run error funnel without masking the primary failure.
- Do not change Phase 05's stream-health encoding/bitrate settings as a substitute for adding real message content.

## Acceptance Criteria

- [ ] Production `run` reads messages from the actual Live Chat associated with its own newly created broadcast using a currently supported official API mechanism.
- [ ] Required scopes/permissions are documented and the existing OAuth credential service is reused; no duplicate OAuth or credential format is introduced.
- [ ] Supported text-bearing messages are mapped to the existing `ChatMessage` model with correct ID/timestamp metadata and normalized single-line display.
- [ ] Messages are appended to the existing chat log and bounded visible queue, then rendered into the production YouTube stream.
- [ ] Video generation and FFmpeg streaming remain continuous when chat is empty, slow, reconnecting, or unavailable according to the documented policy.
- [ ] Polling/streaming, retries, buffers, cancellation, and shutdown are bounded; server-provided intervals/tokens or streaming reconnect semantics are respected.
- [ ] YouTube-specific models remain in `src/youtube/`; the renderer, ChatStore, and streaming modules do not depend on YouTube API types.
- [ ] Chat/API failures are typed, actionable, secret-safe, and reach the production run error policy without masking primary failures.
- [ ] `demo`, local MP4 behavior, Phase 05 RTMPS settings, secret redaction, and clean Ctrl+C shutdown remain regression-tested.
- [ ] Offline tests pass without real Google access, real credentials, or real broadcasts.
- [ ] Docker dev checks pass and Linux/Windows release artifacts are rebuilt, or exact blockers are documented without claiming success.
- [ ] Documentation, project structure/context, and a tracked Phase 06 completion report accurately describe implementation and verification.
- [ ] No credentials, tokens, authorization headers, stream keys, RTMPS URLs, generated videos, logs, or build artifacts are committed.
