# Phase 07 — YouTube Live Chat streamList Migration (Real-Time Retrieval)

## Objective

Replace the Phase 06 polling-based production retrieval (`liveChatMessages.list` at the server-directed interval) with the low-latency server-streaming retrieval (`liveChatMessages.streamList`), so incoming chat messages appear in the rendered video as they are pushed instead of on the next poll tick. Motivation (operator, 2026-10-29): the polling build works end-to-end, but messages visibly lag in the video, and shortening the poll interval would burn quota faster; `streamList` removes constant per-interval calls entirely — the API is called only to establish or re-establish the stream.

This TODO **supersedes the D-1 verdict** of `.kilo/plans/20261025-phase06-task1-live-chat-research-design.md` by explicit USER RULING (2026-10-29) — not by new official evidence alone. Task 1 must still re-verify current official documentation (access-dated) and may surface a STOP if official facts make the ruled direction infeasible; otherwise it implements the user-ruled direction.

## Scope and Boundaries

- **User ruling:** `streamList` is the production retrieval strategy. The server-streaming connection is established when the broadcast's chat becomes available, kept open for the session, and re-established (with the last `nextPageToken`) on drop — never re-called on a fixed/periodic schedule. Polling loops must not remain the primary pacing mechanism.
- **Client path is a research-adjudicated choice, not an assumption.** The previous record (S4) found the OFFICIAL client is gRPC server-streaming over HTTP/2 with Google's published proto; the REST mirror (`GET youtube/v3/liveChat/messages/stream`) exists in the discovery document but NO official wire/behavior documentation for a plain-HTTP streaming body was found (no chunking/keepalive semantics). Task 1 must decide, with official citations and access dates:
  - Path A: official gRPC client (generated stub from the published proto; Rust: `tonic` + `prost` + `tokio` or `grpcio`) — evaluate MSRV/toolchain compatibility against the pinned `rust:1.82` image and the Windows GNU cross-build BEFORE implementing; if no compatible version exists, STOP and surface the toolchain-pin decision to the caller (never silently bump the image).
  - Path B: HTTP streaming over the existing sync stack (ureq) IF AND ONLY IF an officially documented wire format for the REST mirror is found (payload framing, chunk/keepalive semantics, error propagation mid-stream).
  - Path C: if neither is OFFICIALLY implementable, STOP and report back to the caller with the evidence.
- **External guidance context (user-supplied, from a third-party AI):** the caller pasted directives recommending "Reqwest+Tokio, `bytes_stream()` line-by-line reading" against `GET .../liveChatMessages/streamList`, an async bounded `tokio::sync::mpsc` queue, typed serde structs for `textMessageEvent`/`superChatEvent`/`userBannedEvent`/`tombstone`, and a self-healing backoff loop keyed on `nextPageToken`. These are INPUTS to evaluate, not verbatim specifications: Task 1 must verify each claim against current official docs and explicitly record which are confirmed, which are undocumented assumptions, and which contradict project rules (e.g., "or API key query param" contradicts the project's Bearer-only OAuth rule; an async `tokio::sync::mpsc` queue between the worker and the frame loop contradicts the existing bounded std seam unless adjudicated; `superChatEvent` etc. exceed the project's text-only message policy).
- Preserve the application-level boundaries exactly: provider messages still map to the existing `ChatMessage` model (`textMessageEvent`-only policy per brief §8.2 and the Phase-06 mapped policy; other event types skipped per the documented, tested policy; provider metadata never becomes visible text); messages still flow `MessageSource → ChatStore (log-first) → renderer → frame pipeline` with one message consumed per frame iteration; the bounded visible queue and append-only chat log contracts are unchanged.
- Preserve the startup/shutdown architecture: the chat worker remains spawned at the confirmation gate's `Confirmed` outcome and joined after the sink EOF inside `gate.finish()`; the bounded channel between the worker and the frame loop is the existing std `sync_channel` unless a change is adjudicated in Task 1; if a Tokio (or other async) runtime is introduced, it MUST be confined to a dedicated thread with an explicit, bounded, cancellable bridge into the synchronous frame loop, documented in `tech.md`.
- Preserve the resumability semantics: dedup by provider message ID across reconnects (512 window), no history replay after reconnect, no restoration of old log records into the visible queue; verify officially how `streamList`'s initial deliveries and `pageToken` resume interact with the baseline-history-discard requirement (brief §8.3: the stream starts with an empty chat display).
- Preserve every regression lock: `demo`'s deterministic schedule and local MP4 arguments byte-stable; the RTMPS argument vectors, secret redaction, the single-`error:`-line contract, exit-code tables, and the clean Ctrl+C stop (exit 0) all untouched; Phase-05 stream-health settings untouched. No credentials, tokens, authorization headers, raw response bodies, stream keys, or RTMPS URLs are ever logged.
- Keep the bounded, cancellable worker contract: a stalled or dropped stream connection must not hang the frame loop or the shutdown; reconnect attempts are bounded (documented backoff with a cap and a consecutive-failure budget consistent with the existing terminal classes); ChatEnded/disabled chat/permission failures still reach the typed `ChatRetrievalError` funnel.
- Automated tests remain offline: fake stream transports/sources (and loopback servers where the chosen path makes them practical — e.g., a loopback gRPC server under a Tokio test runtime for Path A) only; no test contacts Google.
- Documentation must record the changed latency/quota profile honestly: the new expected message-appearing latency (official "low latency" characterization + the push mechanics), the streaming-call quota billing semantics AS DOCUMENTED (including any uncertainty — never invent unit math for semantics the docs do not state), operator implications, and the updated failure/recovery/privacy guidance. The operator-run manual E2E procedure gains the latency-observability expectation; live claims stay operator-run, never agent evidence.
