# Stream Establishment Panic Fix (readiness reserve + worker panic funnel)

## Objective

Fix the `run` chat-retrieval worker panic that killed message delivery on the streamList build, and harden the retrieval worker so an in-thread panic can never again produce a mute failure. Trigger (OPERATOR-SUPPLIED FACTS, `logs/run/20261030-211225.log`, never agent-observed live): two `run` sessions on v0.13.0 (broadcasts `TUcJ71xiBqM`, `WebHLRIOlvo`) both started, confirmed active, resolved the live chat id — then the worker thread panicked at the `.open()` call; the stream kept working; NO chat message ever rendered, and the run exited 0 without any `error:` line.

## Pre-Diagnosis (recorded by the Planner, 2026-10-30; binding input, not an assumption)

- **Panic site (operator log, both runs):** `thread '<unnamed>' panicked at .../tower-0.5.3/src/buffer/service.rs:122:23: \`send_item\` called without first calling \`poll_reserve\``; run 2's `RUST_BACKTRACE=1` stack: `PollSender::send_item` → `tower::buffer::Buffer::call` → `<tonic Channel as tower_service::Service<...>>::call` → `<GoogleLiveChatStreamTransport as ChatStreamTransport>::open::{{closure}}` → `run_stream_loop::{{closure}}`.
- **Root cause, pinned from the locked source:** tonic 0.13.1's `Grpc::streaming` (the path under `server_streaming`; `src/client/grpc.rs:282–319`) calls `self.inner.call(request)` WITHOUT first calling `Grpc::ready()` — but `Grpc::ready()` exists on the same type (`grpc.rs:199–204`) and the transport `Channel` implements the tower `Service` contract where `call` MUST follow a `poll_ready` on the same handle (the `Channel` is backed by `tower::buffer::Buffer`, which panics otherwise). Independent confirmation: tonic issue #2555 (identical panic without reaching the server) and multiple real-world client implementations documenting "the channel is backed by a tower Buffer whose call panics if poll_ready was never polled — reserve with `client.ready().await` before call(); generated tonic clients do this too".
- **Conclusion:** Phase-07 Task-2's `open()` skeleton omitted the `ready()` step before `server_streaming` — a plan defect in our call shape (NOT a crate-version defect; tonic 0.13.1 requires `tower ^0.5` and no 0.5.4+ patch exists on crates.io as of 2026-10-30 to route around it). The first `.open()` call panics the worker thread deterministically before any server contact.
- **Why it was mute:** the worker thread's unwind is discarded at `src/app/run/gate.rs:188` (`let _ = worker.join()`); `gate.finish()` joins after sink EOF; the terminal cell was never written; the frame loop observed only `Disconnected` + empty cell → `Ok(None)` forever; the run exited 0. The video pipeline was healthy throughout — retrieval alone died.
- **Secondary shaping facts (from the same log):** `enableAutoStop` auto-completed both broadcasts after ingestion ended (no live orphan remains; the operator should still glance at Studio per the fate policy); both video encodes were healthy (CBR ~5989/5965 kbit/s, clean exits).
