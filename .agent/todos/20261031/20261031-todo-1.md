# TODO — Configurable Observability and Game-Foundation Handoff

## Objective

Improve the ability to explain and measure end-to-end Live Chat-to-viewer latency, using the operator-observed baseline of approximately **35 seconds** from sending a chat message to seeing it in the YouTube player as the motivating case.

At the same time, make this repository's existing streaming implementation understandable and practical as the foundation for a future chat-controlled 2D/2.5D game.

This TODO covers implementation, verification, and documentation only. It does not implement game mechanics, change the YouTube streaming architecture, or attempt to optimize latency before measurements identify a bottleneck.

Observability features must be independently configurable and disabled by default wherever practical, so production/game deployments can turn off diagnostic overhead and output without removing the instrumentation code.

## Context and Constraints

- The production `run` path uses YouTube Live Chat's server-streamed `streamList` transport, a dedicated chat worker, a bounded worker-to-frame channel (capacity 64), a synchronous frame loop, a renderer, and an external FFmpeg process that sends video to YouTube over RTMPS.
- The frame loop currently consumes at most one queued chat message per frame iteration. At 30 FPS, this is a nominal consumer ceiling of approximately 30 messages/second; sustained arrival rates above the consumer rate can create backlog even though memory remains bounded.
- The observed ~35 seconds is an end-to-end viewer measurement. It includes upstream chat delivery, application processing, encoding/ingest, YouTube live processing, and viewer playback buffering. Do not attribute it to any one stage without measurements.
- The app cannot directly observe when a viewer's player displays a frame. Viewer-side latency therefore requires a documented external measurement procedure and must be reported separately from application-internal timings.
- Preserve the current bounded-memory and backpressure behavior. Do not add unbounded queues, silently drop messages, or weaken shutdown guarantees to improve apparent latency.
- Preserve `auth`, `demo`, and `run` behavior unless a narrowly scoped change is required and covered by tests. `demo` must remain local-only and must not contact YouTube.
- Follow the repository's current architecture and coding conventions. Read `.agent/project-structure.md` before adding source files and update it if the structure changes.
- Treat `.agent/project-info/brief.md` as the source of truth if any project-info summary conflicts with it.

## Tasks

### Task 1 — Add opt-in, low-overhead pipeline observability

Instrument the production chat-to-frame-to-FFmpeg path so an operator can determine where application-internal delay or backlog occurs.

Requirements:

- Review the current chat worker, channel handoff, frame loop, renderer, FFmpeg writer, configuration model, logging initialization, and production documentation before choosing instrumentation points.
- Add a dedicated configuration section for diagnostics/observability. Every optional diagnostic feature must be explicitly configurable and disabled by default. Use the existing strict configuration validation conventions and update `config/config.example.json` and configuration documentation.
- Provide independently switchable capabilities where useful, rather than one indivisible debug mode. At minimum consider:
  - pipeline timing events;
  - periodic aggregate metrics summaries;
  - queue/backpressure diagnostics;
  - structured diagnostic event output to a separate file.
- Record per-message timing/correlation data without logging message text, OAuth material, stream keys, or other secrets. Use the provider's message identifier as a correlation key where available; do not introduce user-identifying data into metrics.
- Capture the following timestamps/stages where technically available:
  1. provider message publication timestamp (`publishedAt`, clearly identified as provider-supplied wall-clock time);
  2. local message receipt from the `streamList` response;
  3. successful enqueue into the bounded application channel;
  4. dequeue/consumption by the frame loop;
  5. frame render completion containing the message;
  6. start and completion of the corresponding frame write to FFmpeg stdin.
- Use monotonic clocks for local duration calculations. Keep wall-clock timestamps only where cross-system correlation is necessary. Do not subtract timestamps from different clock domains and present the result as a precise duration without stating the clock-skew limitation.
- Record queue depth when observable, high-water mark, enqueue wait/failure/full-channel events, oldest queued-message age, messages received/rendered per interval, and reconnect count/duration. Distinguish a message retained by the worker during backpressure from a message successfully enqueued.
- Add frame-pipeline measurements that can reveal slow rendering or FFmpeg stdin writes, including frame-loop interval/jitter and render/write duration. Avoid emitting one log line per frame in normal operation.
- Aggregate useful distributions (at least count, min/max, mean and percentile or histogram buckets where feasible) rather than relying only on averages. Keep the implementation bounded in memory.
- If diagnostic events are written to disk, make output location configurable, keep it separate from the ordinary chat log, and provide bounded rotation/size or another explicit disk-growth limit. Do not create unbounded diagnostic files.
- Ensure disabling all observability options avoids diagnostic file creation and high-frequency event formatting/writes; document any unavoidable minimal baseline overhead.
- Do not add a metrics server, dashboard, external telemetry service, or new runtime dependency unless the implementation plan establishes a concrete need. Prefer the existing `tracing` stack and standard-library facilities where sufficient.
- Add unit tests for timestamp propagation, duration calculations, aggregation, configuration defaults/validation, and disabled-mode behavior. Use deterministic clocks or injected test values instead of sleep-based timing tests.
- Preserve existing error redaction and one-line CLI error contracts.

Acceptance criteria:

- With all observability options omitted/disabled, `auth`, `demo`, and `run` retain their documented behavior and no diagnostic artifact is created.
- Enabling diagnostics produces enough correlated data to separate chat delivery/worker delay, channel backlog, frame/render delay, and FFmpeg write delay.
- Metrics remain bounded in memory and diagnostic disk output is bounded when enabled.
- No chat body, access/refresh token, OAuth client secret, RTMPS URL, or stream key appears in diagnostic output.
- Automated tests cover enabled, disabled, invalid configuration, aggregation, and backpressure cases.
- Existing development checks, tests, formatting, and clippy gates pass.

### Task 2 — Add reproducible latency, throughput, and backpressure test maps

Create repeatable tests and operator procedures that use the observability added in Task 1 to characterize the application without depending on live YouTube for every test.

Requirements:

- Define a documented test map that follows one synthetic chat message through receipt, enqueue, dequeue, render, and FFmpeg-write boundaries. Identify which timestamps are measured by the application and which require an external observer.
- Add deterministic automated tests around the real queue/consumer behavior or the narrowest existing production seams, without calling Google/YouTube. Verify:
  - low message rates that remain below frame consumption capacity;
  - bursts that temporarily fill the channel;
  - sustained input rates below, near, and above the nominal frame-consumption rate;
  - recovery after a burst drains;
  - bounded memory and no silent mid-session message loss;
  - the documented shutdown behavior when messages remain queued.
- Add a repeatable load/stress harness or test utility that can inject controlled message rates and burst sizes into the application pipeline. It must not require live credentials or create a YouTube broadcast.
- Use the current configured FPS and channel capacity as inputs to test scenarios; do not hardcode 30 FPS as a universal assumption. Explain that the current one-message-per-frame consumer design gives a nominal capacity of one message per frame.
- Report throughput, queue high-water mark, queue age, enqueue-to-render latency, render duration, and FFmpeg-write duration. Clearly distinguish synthetic pipeline measurements from actual YouTube end-to-end latency.
- Define thresholds as diagnostic observations or regression guards only when justified by measured behavior. Do not claim that synthetic tests reproduce YouTube's server delivery or viewer buffering.
- Document an operator-run live test using a separate viewer/chat account:
  - record the sender's send time and the viewer's first-visible time using a consistent clock or a clearly described manual stopwatch method;
  - repeat enough times to avoid treating one observation as a stable baseline;
  - record the broadcast/player latency mode and relevant playback conditions when available;
  - correlate each test message with application diagnostic events using its message identifier;
  - record the end-to-end result separately from internal stage durations;
  - compare runs with observability enabled and disabled to identify instrumentation overhead.
- Include a results template with run/build identifier, date/time, configured FPS, diagnostics settings, message rate/burst profile, queue metrics, internal timing summaries, external viewer delay, and notes.
- Document the interpretation matrix: upstream delivery delay, application queue delay, frame/render delay, FFmpeg/ingest delay, and YouTube viewer playback delay. State which stages the app can measure directly and which are only externally inferred.
- Keep all live YouTube tests explicitly operator-run. Automated checks must remain offline and must never claim to verify Google service behavior.

Acceptance criteria:

- A deterministic offline test suite exercises low-rate, burst, and sustained-over-capacity scenarios.
- The harness can demonstrate whether queue backlog is stable, drains, or grows under each scenario.
- Test output distinguishes application-internal latency from viewer end-to-end latency.
- A documented operator procedure can reproduce and record a viewer-side measurement comparable to the observed ~35-second result.
- No automated test requires OAuth credentials, a live broadcast, or a public YouTube stream.

### Task 3 — Document how to use this repository as the foundation for a chat-controlled game

Audit existing documentation for gaps and create a practical developer/AI-agent handoff guide. The goal is to let a future implementation agent understand what is reusable, where game-specific code belongs, and which infrastructure must remain stable.

Requirements:

- Describe the current executable modes and their responsibilities:
  - `auth`: interactive OAuth authorization and credential persistence;
  - `run`: production broadcast lifecycle, Live Chat `streamList` ingestion, frame production, FFmpeg, RTMPS, and shutdown;
  - `demo`: local-only deterministic MP4 recording through the shared chat/render/frame/FFmpeg pipeline, with no YouTube access.
- Document the current runtime data flow and actual source-module locations, using the repository as it exists at implementation time. At minimum explain the responsibilities and boundaries of:
  - `src/app/` orchestration and pipeline;
  - `src/config/` validated configuration;
  - `src/youtube/` OAuth, broadcast/stream lifecycle, and Live Chat transport;
  - `src/chat/` application-level message model and bounded visible-message store;
  - `src/renderer/` render input, renderer contract, and RGB24 frame production;
  - `src/streaming/` FFmpeg process and stdin frame delivery.
- Explain which existing components should be reused unchanged by a game implementation and which are intended extension points. Explicitly state that game logic must not depend on YouTube API types, OAuth, broadcast IDs, RTMPS URLs, or FFmpeg command details.
- Define a recommended future game-oriented flow, without implementing it in this TODO:
  `YouTube Chat Adapter -> ChatMessage -> Command Parsing/Validation -> Game Input/Events -> Game State Update -> Render State -> Renderer -> RGB24 Frames -> FFmpeg -> YouTube Live`.
- Explain the separation between:
  - transport messages and validated game commands;
  - command parsing/authorization/rate-limiting and game rules;
  - authoritative game state and render-only state;
  - deterministic game update/tick logic and frame rendering;
  - game simulation cadence and video output FPS.
- Include guidance for an agent implementing the first game prototype:
  1. inspect `AGENTS.md`, project-info, workflows, rules, and project structure first;
  2. inspect the existing contracts and tests before changing code;
  3. preserve `auth`, `demo`, and `run` contracts;
  4. add game-specific modules behind application-level interfaces rather than embedding game rules in YouTube or FFmpeg modules;
  5. keep game state independent of renderer implementation;
  6. make update logic deterministic and unit-testable;
  7. define explicit policies for command validation, permissions, spam/rate limiting, queue overflow, and simultaneous inputs before implementation;
  8. add a deterministic local demo/test source so game behavior can be developed without a live broadcast;
  9. avoid introducing a new async runtime or changing the chat worker's runtime ownership without an architectural reason;
  10. update project structure, configuration examples, documentation, and project-info when architecture changes.
- Explain timing and scale constraints relevant to a multiplayer/chat-controlled game:
  - YouTube Live Chat is not a real-time game networking transport and viewer playback is delayed;
  - the 35-second viewer observation is a current operator measurement, not a guaranteed platform constant;
  - player actions should be designed around delayed/asynchronous input (turn-based, queued, voting, or other latency-tolerant mechanics) unless future measurements and product decisions justify another model;
  - distinguish number of viewers from message throughput; load is driven by message rate/bursts and processing cost, not viewer count alone;
  - preserve bounded queues and define overload behavior explicitly;
  - 1080p/4K output resolution affects frame memory, rendering cost, and encoding bandwidth, not the timing semantics of chat delivery.
- Add a concise decision checklist and a "what not to change" section for future agents.
- Cross-link the guide from the README and relevant architecture/development/production docs. Avoid duplicating long operator procedures; link to the canonical docs.
- Update `.agent/project-info/architecture.md`, `.agent/project-info/tech.md`, and `.agent/project-info/context.md` if implementation reveals lasting architectural facts or new next steps. Keep `AGENTS.md` links accurate if new project-info files are added.
- Keep documentation focused and split into appropriately sized files with a table of contents for documents exceeding 100 lines.

Acceptance criteria:

- A future agent can identify the reusable streaming infrastructure, application extension points, and safe places to add game logic without guessing.
- The guide describes actual current code paths and contracts, not only the original project brief's intended architecture.
- It includes an explicit latency warning and recommends latency-tolerant game mechanics as the default starting point.
- It documents a local/offline development path that does not require OAuth or a live YouTube broadcast.
- README and relevant documentation link to the guide; project-info summaries are consistent with the implemented architecture.
- No game mechanics or game-specific runtime behavior are implemented as part of this task.
